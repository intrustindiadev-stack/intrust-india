02 · Executive Vision

Executive vision

From smarter replies
to completed requests.

the shift that matters
INTRUST · AGENTIC AI

InTrust already captures demand at the moment of intent — in chat, on the storefront, in the merchant's daily operations. Today that conversation ends with information. The opportunity is to let it end with a result: an item added, an order explained, a merchant question answered from their own data, a cart prepared for a secure checkout.

Today — the assistant answers
  • Answers a question and stops at information.
  • Explains steps the user must then perform manually.
  • Hands the user off to a sequence of screens.
  • Every journey restarts from the beginning.
Proposed — the agent completes
  • Understands intent from text, image, voice or a mix.
  • Assembles only the context the signed-in user is allowed to see.
  • Selects an approved capability from a fixed registry.
  • Completes the request through the workflows InTrust already runs.

Fewer steps to the same outcome

Natural language replaces multi-screen navigation, so demand is acted on while it is still fresh.

The trust model stays intact

Authentication, permissions and business rules remain the authority. The agent operates inside them.

One foundation, two audiences

The same intelligence layer serves customers and merchants through different permissions.

Agentic architecture

One intelligence layer.
Zero parallel systems.

an action layer, not a rebuild

The agent sits between the user's conversation and the services InTrust already operates. It interprets the request, assembles permitted context, chooses from a fixed set of registered capabilities, and hands execution to the platform. Every result travels back through the same path in reverse — so the conversation never becomes a second source of truth.

Interfaces

Customer conversation, merchant assistant, voice & image input.

Result

What the layer adds

New
Intent understanding across text, image and voice.
Context assembly limited to the caller's permissions.
Capability selection from an explicit, reviewed registry.
Guardrails, rate limits and loop protection on every request.
Traceability: request, selection and outcome are all recorded.

What stays exactly as it is

Reused
Authentication — existing sessions and sign-in flows.
Permissions — the same ownership and access rules.
Business logic — pricing, availability, eligibility, fulfilment.
Data — one catalogue, one cart, one order record.
Audit — the platform's own logs remain authoritative.

No duplicate backend

The agent calls services, it does not recreate them.

Observable by default

Each hop can be inspected without changing the platform.

Reversible

Capabilities can be enabled or withdrawn independently.

Integration surface — proposed

The agent calls existing service endpoints, not raw tables.
Identity and permissions are resolved server-side from the session.
Read-only context is enabled first; write actions follow capability by capability.
No schema change is required to add the layer.

Behaviour when something fails

The user is told what could not be completed, in plain language.
No partial state is hidden — the conversation reflects reality.
Retries are bounded; the agent never loops indefinitely.
Every failure is logged with the capability that was attempted.
Design ruleIf a request cannot be served by a registered capability, the agent explains the limitation and routes the user to the normal journey. It never improvises a workaround.

Context & reasoning

Reasoning is only as good
as the context behind it.

remember only what is yours
Context assembled per request
  • Conversation so far — what the user actually said.
  • Permitted profile context, already available in the account.
  • Permitted order, cart and wishlist history for that account.
  • Live catalogue, stock and price at the moment of asking.
Decision reached — and explainable
  • One intent, one capability, chosen from the registry.
  • The reason for the selection can be described to the user.
  • Every factual value comes from a platform response, not a guess.
  • If context is insufficient, the agent asks instead of assuming.

Context it never uses

Data belonging to another customer or merchant.
Anything the signed-in user is not permitted to see in the panel or app.
Raw database tables or internal endpoints outside the capability list.
Assumptions about price, stock or eligibility that no service confirmed.
Anything the model “remembers” outside the current session's approved context.

Principles we hold to

Context is requested, scoped and perishable — never a silent profile.
Facts come from services; the model contributes language, not data.
Ambiguity is resolved by asking, never by guessing on the user's behalf.

Context is fetched, not assumed

Values are read from the platform at the moment of the request, never from memory.

The user can see why

When the agent makes a choice, it can explain which request and which data led to it.

Refusal is a valid outcome

If context or permission is missing, saying so is the correct answer — not a workaround.

Sequencing principles

Read before write. Understanding the data comes first; state changes come later.
Reversible before irreversible. Cart and wishlist precede anything final.
One audience at a time. Customer experience is proven before merchant operations.
Capability by capability. Each addition is reviewed and can be withdrawn.

How we would know a phase worked

Requests are being understood and completed without manual intervention.
Every action is traceable back to a capability and a permission outcome.
Users and merchants complete the intended task more directly than before.
Support questions about “how do I…” reduce for the journeys in scope.

What we would need from InTrust

A named owner for capability approval — additions signed off by the business, not by the build.
Existing role definitions and permission outcomes, so the agent inherits them exactly.
Access to the catalogue, stock and order services the panel already uses.
A contact for incident and rollback decisions once a phase is live.

Held back on purpose

No payment, wallet, OTP or credential handling inside the agent.
No pricing, discount or eligibility logic invented by the model.
No direct database access — every read and write uses an existing service.
No autonomous change to a merchant’s records without confirmation.

A small group observed closely in each phase
A feedback loop
Observations feed the next capability review

How we would read the signals

Where requests are clarified too often, the capability or the copy is wrong.
Where users still leave the conversation, the hand-off needs designing better.
Where the agent refuses, the registry may simply need one more approved action.

What we would measure at each horizon

Where requests resolve in one turn, and where they need clarifying.
Whether users reach checkout or a decision without leaving the conversation.
How often the agent refuses — and whether a missing capability caused it.
Whether every action maps back to an approved capability and permission.

What we would deliberately avoid

Adding autonomy before the data and permissions beneath it are trusted.
Letting the assistant become a second source of business rules.
Broadening scope for its own sake — capability only where it earns its place.
Any horizon that cannot be switched off cleanly.
