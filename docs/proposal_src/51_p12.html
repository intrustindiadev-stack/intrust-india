Phased roadmap

Phased by design.
Every phase stands alone.

start small, prove it, expand

Nothing here needs to be delivered at once. Each phase ends with something usable and observable, and each one is independently valuable to InTrust. If priorities change, the work to date remains in place.

01
Foundation
The intelligence layer exists
  • Agent framework and request path
  • Capability registry — read-only first
  • Permission checks wired to existing roles
  • Guardrails, rate limits, loop protection
  • Audit and observability from day one
02
Customer agent
Shopping in a sentence
  • Product discovery and search
  • Filters by price, size and availability
  • Product and availability questions
  • Wishlist add and remove
  • Cart add, update and order lookup
03
Multimodal
Show it, say it
  • Image-based product discovery
  • Voice input with transcription
  • Mixed requests — image plus constraint
  • Refinement and correction in thread
  • Consistent handling across modalities
04
Merchant assistant
The business answers back
  • Order counts, status and dispatch
  • Inventory and low-stock insight
  • Revenue and repeat-customer metrics
  • Business and subscription status
  • Serviceability and policy answers
05
Automation
Fewer steps, still governed
  • Multi-step requests handled in one turn
  • Proactive prompts based on permitted events
  • Policy-driven confirmation rules
  • Additional reviewed capabilities
  • Deeper personalisation within scope

Sequencing principles

Read before write. Understanding the data comes first; state changes come later.
Reversible before irreversible. Cart and wishlist precede anything final.
One audience at a time. Customer experience is proven before merchant operations.
Capability by capability. Each addition is reviewed and can be withdrawn.

How we would know a phase worked

Requests are being understood and completed without manual intervention.
Every action is traceable back to a capability and a permission outcome.
Users and merchants complete the intended task more directly than before.
Support questions about “how do I…” reduce for the journeys in scope.

What we would need from InTrust

A named owner for capability approval — additions signed off by the business, not by the build.
Existing role definitions and permission outcomes, so the agent inherits them exactly.
Access to the catalogue, stock and order services the panel already uses.
A contact for incident and rollback decisions once a phase is live.

Held back on purpose

No payment, wallet, OTP or credential handling inside the agent.
No pricing, discount or eligibility logic invented by the model.
No direct database access — every read and write uses an existing service.
No autonomous change to a merchant’s records without confirmation.
A design-partner cohort
A small group observed closely in each phase
A feedback loop
Observations feed the next capability review
A rollback path
Any capability off, without touching the platform
“A phase that cannot be measured is a phase that cannot be trusted. Each stage ends with evidence, a reference list of capabilities, and a clear decision to continue.
