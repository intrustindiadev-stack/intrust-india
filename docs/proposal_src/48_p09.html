Context & reasoning

Reasoning is only as good
as the context behind it.

remember only what is yours
Context assembled per request
  • Conversation so far — what the user actually said.
  • Permitted profile context, already available in the account.
  • Permitted order, cart and wishlist history for that account.
  • Live catalogue, stock and price at the moment of asking.
Decision reached — and explainable
  • One intent, one capability, chosen from the registry.
  • The reason for the selection can be described to the user.
  • Every factual value comes from a platform response, not a guess.
  • If context is insufficient, the agent asks instead of assuming.

Context it never uses

Data belonging to another customer or merchant.
Anything the signed-in user is not permitted to see in the panel or app.
Raw database tables or internal endpoints outside the capability list.
Assumptions about price, stock or eligibility that no service confirmed.
Anything the model “remembers” outside the current session's approved context.

Principles we hold to

Context is requested, scoped and perishable — never a silent profile.
Facts come from services; the model contributes language, not data.
Ambiguity is resolved by asking, never by guessing on the user's behalf.

Context is fetched, not assumed

Values are read from the platform at the moment of the request, never from memory.

The user can see why

When the agent makes a choice, it can explain which request and which data led to it.

Refusal is a valid outcome

If context or permission is missing, saying so is the correct answer — not a workaround.

“Context is what makes an agent useful. Permission is what makes it safe. InTrust's agent would hold both — and never confuse one for the other.
